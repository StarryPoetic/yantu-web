# 研途长期单实例部署

更新日期：2026-11-13。[免费公网测试站](免费公网测试站.md)已完成 Render Free 上线与有限公网流程验收；它使用临时 SQLite、示例数据并关闭模型与搜索。长期生产服务器、自有域名和持久化灾备仍待验收。本文件及 [systemd 服务模板](../deploy/yantu.service)、[Caddy 模板](../deploy/Caddyfile)用于长期部署准备，尚未在实际 Linux 服务器执行；备份保留、定时器和隔离恢复工具已提供但默认不启用，没有集群或长期可用性承诺。

## 1. 部署形态与目录

使用一台 Linux 主机、一个 Node.js 应用进程和本机 SQLite 数据库。Caddy 在 80/443 接收请求并处理 HTTPS，转发到 `127.0.0.1:8787`；应用提供 `dist` 页面和 `/api/v1`。后端端口不对公网开放，不使用 PM2 多进程或多副本。

| 路径 | 内容及权限 |
| --- | --- |
| `/opt/yantu/releases/<Git提交>` | 对应提交的应用、`dist`、`server`、`shared`、`knowledge` 和运行依赖；部署人员维护，应用只读。 |
| `/opt/yantu/current` | 当前发布目录的符号链接，systemd 的固定工作目录。 |
| `/etc/yantu/yantu.env` | 服务端配置，建议 root 所有、权限 `0600`；不放在代码仓库或公开目录。 |
| `/var/lib/yantu/production.sqlite` | 独立生产数据库及 SQLite WAL/SHM 文件，`yantu` 服务账号可写，目录 `0700`。 |
| `/var/lib/yantu-backups` | 手动备份目录，运维人员管理，目录 `0700`；与服务公开静态目录分开。 |

Node.js 必须满足 `package.json` 的 `>=24.14.0` 要求；本轮在 Node.js 24.14.1 验证。该版本支持直接执行本项目 TypeScript 和自带 SQLite。模板的 `/usr/bin/node` 须改为实际 Node 安装路径。源码与运行依赖都需保留，不能只上传 `dist`；`pdf-parse` 的服务端 PDF 解析也需要依赖和独立子进程。

不要把 Windows 本地示例数据库直接作为正式数据库。生产环境自动禁用示例数据，含活动示例发布的数据库会被拒绝；首次正式启动建立空资料库，真实招生资料、规则及题库需通过后台独立复核后发布。

## 2. 配置与首次启动

先完成 `npm ci`、`npm run check`，再准备发布目录。首次部署需创建系统账号 `yantu`、上表中的目录及受保护配置，并保证应用账号能写数据库目录、能读发布目录。已有服务器时再执行这些操作。

`/etc/yantu/yantu.env` 的基础配置如下；域名只是占位符，必须替换为实际 HTTPS 来源。生产 `YANTU_DATABASE_PATH` 必须显式指定绝对文件路径，不能使用相对路径、内存数据库或开发默认路径。

```dotenv
NODE_ENV=production
HOST=127.0.0.1
PORT=8787
YANTU_ORIGIN=https://your-domain.example
YANTU_DATABASE_PATH=/var/lib/yantu/production.sqlite
YANTU_SAMPLE_DATA=false
YANTU_TRUSTED_PROXY_IPS=127.0.0.1
YANTU_MODEL_ENABLED=false
YANTU_SEARCH_ENABLED=false
```

模型与搜索按 [.env.example](../.env.example) 和 [本地模型与联网测试](本地模型与联网测试.md)配置，凭据只写入受保护环境。初始化管理账号时使用 `YANTU_BOOTSTRAP_ADMINS`，提供独立的录入、复核和发布身份；首次创建并确认可登录后移除明文初始化值。已有学生不会因配置而自动提升权限，既有管理员密码也不会被覆盖。systemd 环境文件只支持环境赋值，不执行 shell 命令。

`YANTU_TRUSTED_PROXY_IPS` 默认为空，表示只按连接来源限流，忽略客户端的转发 IP。只有本机 Caddy 的实际来源 `127.0.0.1` 被显式加入后，应用才接受它提供的单个合法 `X-Forwarded-For`；列表、端口、主机名和无效地址返回 400。API、游客会话和注册登录统一使用该 IP，账户自身限制仍独立生效。模板用 `header_up X-Forwarded-For {remote_host}`覆盖来访者自带的头，防止伪造；这符合 [Caddy 官方头部配置](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#headers)。

该模板仅适用于用户直接连接 Caddy 的单层入口。若以后加入 CDN、额外代理或容器，需要重新确认真实来源与头部覆盖策略，不能把所有私网或任意地址设为可信代理，也不能把客户端提供的多段链直接作为有效 IP。

把服务模板安装到 `/etc/systemd/system/yantu.service`，核对绝对路径与目录权限后执行：

```bash
sudo systemd-analyze verify /etc/systemd/system/yantu.service
sudo systemctl daemon-reload
sudo systemctl enable --now yantu.service
sudo systemctl status yantu.service
curl --fail --silent http://127.0.0.1:8787/api/v1/health
```

服务用独立账号运行，代码只读，数据库目录可写，私有临时目录供 PDF 子进程使用。systemd 自动重启异常退出的进程；正常停止发出 SIGTERM，等待应用关闭作业、HTTP 连接与数据库。短时间内反复失败会被 systemd 限制启动，需要查看日志并修复原因，不能无限重启掩盖数据库或配置错误。

## 3. HTTPS 与上线检查

将真实域名 DNS 指向服务器，开放必要的 80/443 入口，将 Caddy 模板中的域名替换为与 `YANTU_ORIGIN` 一致的来源。Caddy 配置只反向代理应用，不公开数据库、配置或备份目录。启用前验证实际配置：

```bash
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl reload caddy
curl --fail --silent https://your-domain.example/api/v1/health
```

健康接口执行真实数据库表查询，正常返回 HTTP 200、`status=ok`、`database=ok`、`sampleData=false`；数据库不可读返回 HTTP 503和通用说明，不输出文件路径、SQL 或原始异常。它不检查模型/搜索供应商是否可用，也不代表已经存在已审核资料。监控以低频请求该接口，避免监控自身耗尽 API 限流额度。

上线前实际检查 HTTPS 登录/退出、Secure/HttpOnly Cookie、画像保存及重新登录恢复、两名独立学生账号隔离、后台权限与独立复核、报告下载、删除后的旧请求不能回写、模型/搜索配置缺失时如实降级。确认后端仅监听回环地址，并用不同客户连接验证注册与 API 限流不会共用代理 IP。

查看 `journalctl -u yantu.service` 及 Caddy 状态处理异常；日志不得收集密码、会话 Cookie、认证头、完整画像或供应商原始错误。当前没有自动报警或供应商连通监控，部署方需在实际环境配置并演练。

## 4. 手动在线备份

[备份脚本](../scripts/backup-database.mjs)使用 Node 自带 SQLite 在线备份 API。源库可以保持服务运行，已提交 WAL 内容会进入快照；不能通过单独复制运行中的 `.sqlite` 主文件取得可靠备份。SQLite 官方说明在线备份可以创建一致快照，参见 [SQLite Backup API](https://www.sqlite.org/backup.html)。

从发布目录执行以下命令，源库与目标均明确指定，每次目标使用新的文件名：

```bash
node scripts/backup-database.mjs \
  --source /var/lib/yantu/production.sqlite \
  --destination /var/lib/yantu-backups/production-2026-10-04-before-upgrade.sqlite
```

Windows 本地演练也可使用该脚本，路径显式指定，例如：

```powershell
node scripts/backup-database.mjs --source 'D:\yantu-data\production.sqlite' --destination 'D:\yantu-backups\production-2026-10-04-before-upgrade.sqlite'
```

脚本只读源数据库；先在目标目录内建立私有临时快照，再检查 `PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`，同步文件后原子发布。它拒绝覆盖已有目标或源库，不会在源文件缺失时建立空库，失败不会发布成功备份。Unix 临时目录权限 `0700`、备份文件 `0600`；Windows 需另外检查目录 ACL。原子发布依赖同文件系统的硬链接，建议使用服务器本地磁盘；不支持该能力的文件系统会失败，不能据此声称备份成功。

成功退出码为 0，输出仅含状态、目标路径和完整性结果，不输出数据库内容。备份包含个人资料、密码哈希及会话记录，应加密保存、限制访问，并按确定的保留期限清理。SQLite 完整性通过不代表业务引用、删除和资料撤回都符合恢复要求。

已提供 `scripts/managed-backup.mjs` 与默认禁用的 `deploy/backup.example.json`，以及需显式安装/启用的 systemd 定时器模板。默认命令只检查，配置 `enabled:true` 且带 `--apply` 才创建一次备份并清理超过保留数量和最短年龄的归属快照。真实实例尚未启用；频率、保留期、异地加密、删除记录保存和恢复目标仍须确定，并同步个人资料删除页面说明。详见[备份与隔离恢复](备份与隔离恢复.md)。进程被强制终止时可能留下 `.yantu-backup-*` 临时目录；由运维确认没有运行中的备份后，仅清理对应备份目录内的临时文件，不能当作正式快照使用。

## 5. 隔离恢复与版本回滚

不要直接把旧快照覆盖在线数据库。恢复步骤为：

1. 停止公网入口及应用，确认没有其他进程访问 SQLite。记录当前应用 Git 提交、数据库路径和故障时间；若当前数据库仍可读，先按上一节保留新的事故前快照。
2. 保存快照之后发生的可信当前状态库；`scripts/restore-isolated.mjs` 以它保护删除代次、当前账号和密码、个人资源及资料撤回，并清空旧会话/恢复码/幂等回放，只生成新的隔离候选。当前库不可读且没有同等可信状态时拒绝，不能仅凭旧快照开放数据。工具详细边界见[备份与隔离恢复](备份与隔离恢复.md)。
3. 在私有隔离目录复制所选备份，用对应版本应用和独立绝对数据库路径验证，保持模型/搜索关闭、端口仅本机可见。不要把旧库残留的 `-wal` 或 `-shm` 文件混入新副本。
4. 校验数据库完整性及业务引用；在恢复副本中重放删除代次、清除相应个人资源及幂等回放，重新应用资料撤回。撤销快照内旧会话并验证重新登录，以免已经退出的会话恢复有效。
5. 在隔离副本实际验证账号归属、后台职责、资料版本、删除后不可读、被撤回资料不可用及报告依据。研究在途任务按现有规则标记中断失败，不自动进行付费重试。
6. 通过验证后，停机切换为新的数据库文件路径并同步代码版本，核对目录权限；启动应用，再确认健康接口、真实账号隔离与页面后开放 HTTPS 入口。
7. 记录恢复用的快照、验证结果与允许访问的人，按保留策略销毁过期副本。未通过验证继续保留入口关闭，不能将 SQLite 完整性结果当作恢复验收。

发布更新采用独立 `/opt/yantu/releases/<Git提交>` 目录；通过检查后再切换 `current`，重启应用。回滚先确认旧版本兼容当前数据库及资料版本；不兼容时走上面的隔离恢复流程。现有初始化会创建表与索引，不能假定任意未来数据库迁移都可逆。

## 6. 已验证边界与后续验收

本轮自动测试覆盖生产配置隔离、数据库健康故障与错误脱敏、转发 IP 伪造防护、单跳代理限流隔离、在线 WAL 快照、覆盖拒绝、源缺失/损坏和外键失败。测试使用临时数据库和合成账号，没有读取真实学生资料或调用付费模型。

Linux 的 systemd/Caddy 语法与权限、真实域名证书、外部连接、容量、长期监控和实际删除/撤回恢复演练需要服务器就绪后验收。模型/搜索日额度现已通过SQLite事务预占持久化，账号注册登录限流、账户、会话、审计、研究作业与断点也保存在SQLite；活动调用、缓存与一般API限流仍是单进程状态，本部署仍仅支持单应用进程。供应商费用监控与预算须独立设置，应用账本不能当作供应商账单硬上限。资料库全国年度覆盖和题库学科审校仍按 [实施说明](实施说明.md)进行，部署模板不能替代内容审核。
